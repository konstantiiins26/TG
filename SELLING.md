# Продажа: что нужно и почему это не зеркало покупки

Разбор стороны продажи. Часть здесь **проверена интроспекцией** `tonutils`,
часть — **требует подтверждения** и помечена явно. Отличайте одно от другого:
именно смешение проверенного с додуманным и теряет деньги.

---

## 1. Главная асимметрия

Покупка и продажа выглядят симметрично, но устроены совершенно по-разному.

**Покупка — одна транзакция.** Контракт продажи уже существует (его создал
продавец). Вы просто шлёте на него TON:

```
кошелёк ──TON──> контракт продажи ──NFT──> кошелёк
```

**Продажа — это развернуть контракт и отдать ему свой NFT.** Вы становитесь
той стороной, которая создаёт контракт:

```
кошелёк ──деплой──> НОВЫЙ контракт продажи
кошелёк ──NFT─────> он же   (два шага, оба могут упасть по отдельности)
```

Отсюда следствие, которое ломает наивные ожидания: **между этими шагами NFT
может зависнуть**. Если деплой прошёл, а перевод нет — у вас пустой контракт.
Если перевод прошёл на неверный адрес — NFT потерян безвозвратно.

---

## 2. Что даёт tonutils (ПРОВЕРЕНО)

Интроспекция установленного пакета:

```python
NFTTransferBuilder(
    destination: AddressLike,          # кому передаём NFT
    nft_address: AddressLike,          # какой именно NFT
    response_address: AddressLike|None = None,   # куда вернуть излишек
    custom_payload: Cell|None = None,
    forward_payload: Cell|str|None = None,       # ← сюда идут условия продажи
    forward_amount: int = 1,           # нанотоны, пересылаемые получателю
    amount: int = 50000000,            # 0.05 TON на газ перевода
    query_id: int = 0,
    send_mode: SendMode|int = 3,
    bounce: bool|None = None,
)
```

`BaseNFTItem` — только чтение: `get_nft_data()`, `get_transactions()`,
`refresh()`, `run_get_method()`. Все асинхронные.

### Чего в tonutils НЕТ (ПРОВЕРЕНО)

Поиск по всем подмодулям `tonutils.contracts` по ключам
`sale` / `market` / `auction` / `getgems`:

- **модулей — НЕТ**
- **классов — НЕТ** (нашлись только `get_auction_info_get_method` и
  `get_telemint_auction_*` — read-only гет-методы, не создание продажи)

**Вывод: контракт продажи Getgems библиотека собирать не умеет.** Перевести
NFT она может, создать листинг — нет.

---

## 3. Три пути, и у каждого своя цена

### A. Контракт продажи Getgems — «настоящий» листинг

Лот появляется на Getgems, его видят покупатели, работает обычный флип.

**Проблема — ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ:** насколько мне известно, контракты
продажи Getgems при деплое требуют **подписи маркетплейса** (соглашение о
комиссии площадки). Если это так, произвольно развернуть свой контракт и
ожидать, что лот появится на Getgems, **нельзя** — нужен их бэкенд-эндпоинт,
выдающий подписанный payload.

**Это надо проверить до того, как писать код.** Практический способ: выставить
один лот вручную через интерфейс Getgems и посмотреть в explorer, какая
транзакция ушла — из неё видно и опкод, и структуру payload, и участвует ли
подпись площадки. Час работы, который экономит неделю догадок.

Если подпись нужна — путь A требует интеграции с приватным API Getgems, и это
уже совсем другой объём работ, чем «дописать функцию».

### B. Прямой перевод покупателю — работает на tonutils уже сейчас

`NFTTransferBuilder` умеет это без всяких контрактов продажи.

Но это **не флип**: покупателя надо где-то найти и как-то договориться об
оплате. Автоматизации рынка тут нет. Годится для вывода NFT на другой свой
кошелёк, не для торговли.

### C. Ручная продажа — то, что есть сейчас

Бот покупает, вы продаёте руками в Tonkeeper/Getgems и сообщаете боту цену
через `close_position(position_id, sell_price)`. Учёт PnL честный, бэктест
получает реальные данные.

**Именно это сейчас и реализовано** — `close_position()` существует, но её
никто не вызывает автоматически, это функция бухгалтерии.

---

## 4. Транзакция — меньшая половина работы

Даже когда путь A решён, «продавать» — это отдельный слой решений, которого
в боте **нет вообще**:

| Вопрос | Почему это не мелочь |
|---|---|
| **Когда выставлять?** | Сразу после покупки? Через час? Модель прибыли молча предполагает «сразу и по floor». |
| **По какой цене?** | `floor × (1 − undercut)` на момент покупки или на момент листинга? Floor уже уехал. |
| **Floor упал — что делать?** | Переставлять лот ниже (каждая переустановка = газ) или ждать? Без правила бот зависнет с неликвидом. |
| **Сколько ждать?** | Лот висит 5 дней. Фиксировать убыток? Держать? Без таймаута капитал замораживается и риск-лимиты перестают что-либо значить. |
| **Стоп-лосс** | Floor рухнул на 40%. Выходить или пересиживать? |
| **Отмена листинга** | Нужна отдельная транзакция; контракт продажи должен вернуть NFT. |

Бэктест сейчас моделирует выход как «через N часов по floor того момента».
Это **допущение, а не механика**: он не учитывает ни очередь у floor, ни то,
что ваш собственный лот двигает floor, ни отказ покупателей.

---

## 5. Честная оценка

**Покупка** — понятная задача: API проверен, нужен `sale.address`, исполнитель
и ворота testnet. Один заход.

**Продажа** — не задача «дописать функцию», а отдельный кусок работы:

1. выяснить протокол листинга Getgems (нужна ли подпись площадки) — **до кода**;
2. если подпись нужна — интеграция с их API, объём неизвестен, пока не выяснено;
3. двухшаговый деплой+перевод с обработкой зависания между шагами;
4. слой решений о продаже (таблица выше) — по объёму сопоставим с текущим
   слоем решений о покупке;
5. отмена и переустановка листинга;
6. тесты на всё это без сети.

---

## 6. Что рекомендую

**Не гнаться за полной автоматизацией обеих сторон сразу.** Осмысленная
последовательность:

1. **`--record` сейчас** — проверяет парсинг и копит данные, не требует ничего
   из вышеперечисленного.
2. **`--backtest` через 2–3 дня** — отвечает на вопрос, прибыльна ли стратегия
   вообще. Если прогноз расходится с фактом, всё остальное не имеет смысла.
3. **Покупка на testnet** — когда появится доступ к правкам торгового пути.
4. **Полуавтомат**: бот покупает, вы продаёте руками и вводите цену. Это даёт
   реальные данные о продажах — и они нужны, чтобы вообще понять, по какой
   цене и за какое время ваши лоты уходят.
5. **Автопродажа — последней**, уже зная из п.4 реальную механику рынка.

Пункт 4 не компромисс, а способ собрать данные, без которых слой решений о
продаже проектируется вслепую.

# РАЗВЯЗКА: как устроен листинг на Getgems (18.09.2026)

Главный открытый вопрос этого файла — «требует ли листинг подписи
маркетплейса» — закрыт наблюдением реальной транзакции. Пользователь купил
Xmas Stocking #91332 и выставил его обратно; вот что ушло в блокчейн.

## Что видно в Tonviewer

```
a few seconds ago   Send NFT   UQAF...44KF  ->  Getgems Deplo...   Call: 0x00fe0ede
                    Send NFT   Getgems Deplo... ->  UQCc...FX5w
2 minutes ago       NFT Purchase  UQAF...44KF -> UQD6...SC3z       4.49 GRAM
```

После этого владельцем NFT значится `UQCc...FX5w` — новый контракт продажи.

## Механика

1. Владелец делает **обычный `nft_transfer`** предмета на контракт-деплойер
   Getgems, с полезной нагрузкой (op `0x00fe0ede`), описывающей условия продажи.
2. Деплойер **создаёт контракт продажи** и передаёт NFT ему.
3. Владельцем предмета становится этот контракт; продавец сохраняет право
   снять лот и забрать NFT обратно.

**Подписи маркетплейса в транзакции НЕ видно.** Листинг выглядит как операция,
которую отправляет сам владелец, — значит он воспроизводим кодом, и
`NFTTransferBuilder` из `tonutils` для первого шага подходит.

Это снимает опасение, ради которого файл писался: продажа НЕ упирается в
необходимость подписи со стороны площадки.

## Чего ещё не хватает, чтобы писать код

Op-код виден, а СОДЕРЖИМОЕ полезной нагрузки — нет. Чтобы собрать сообщение,
нужны:

- адрес контракта-деплойера Getgems (в интерфейсе он сокращён);
- точная структура payload: цена, адрес получателя выручки, адрес
  маркетплейса, параметры роялти, срок;
- какой газ приложить к самому листингу — **ИЗМЕРЕНО: 0.22 GRAM**.

Всё это лежит в сырых данных той же транзакции (вкладка **Raw Transactions**
или страница конкретного сообщения в Tonviewer). Без них код писался бы по
догадке — ровно то, чего в этом проекте не делают.

## Подтверждённая экономика

Диалог выставления на продажу (цена 5 GRAM):

```
Marketplace fee    0.1 GRAM     = 2.0%
Creator Royalties  +0 GRAM
You Receive        4.9 GRAM
```

Комиссия берётся С ЦЕНЫ ПРОДАЖИ и вычитается из выручки продавца — ровно так,
как считает `compute_net_profit()`. Ставки 2% и 0 подтверждены в третий раз.

Диалог покупки того же лота:

```
NFT Price     4.49 GRAM   (includes service fee and creator royalties)
Service Fee   0.08 GRAM
Network Fee   0.3 GRAM    (the rest will be returned to your wallet)
```

Отсюда `PURCHASE_GAS_TON = 0.3`: столько прикладывает сам Getgems. Стоявшие
там раньше 0.1 были взяты с потолка, и недостача газа уронила бы транзакцию.

## Газ на листинг (измерено)

Диалог подтверждения в кошельке при выставлении лота:

```
0.22 GRAM будет мгновенно списано с вашего кошелька для оплаты комиссии.
~ 0.19 GRAM будет возвращено вам в течение нескольких минут.
```

То есть к сообщению листинга прикладывается **0.22**, безвозвратно уходит
**около 0.03**. Когда листинг будет писаться кодом, прикладывать надо 0.22 —
не меньше: излишек возвращается, недостача роняет транзакцию.

Сводка по газу за полный круг:

| Операция | Приложено | Израсходовано |
|---|---|---|
| Покупка | 0.30 | не измерено |
| Листинг | 0.22 | ~0.03 |

`GAS_FEE_TON = 0.15` в экономике — это оценка безвозвратной стоимости круга.
Измеренные 0.03 на листинге показывают, что она скорее консервативна, чем
занижена; менять её без измерения расхода на покупке не нужно.
