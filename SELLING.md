# Продажа: что нужно и почему это не зеркало покупки

Разбор стороны продажи. Часть здесь **проверена интроспекцией** `tonutils`,
часть — **требует подтверждения** и помечена явно. Отличайте одно от другого:
именно смешение проверенного с додуманным и теряет деньги.

---

## 1. Главная асимметрия

Покупка и продажа выглядят симметрично, но устроены совершенно по-разному.

**Покупка — одна транзакция.** Контракт продажи уже существует (его создал
продавец). Вы просто шлёте на него TON:

```
кошелёк ──TON──> контракт продажи ──NFT──> кошелёк
```

**Продажа — это развернуть контракт и отдать ему свой NFT.** Вы становитесь
той стороной, которая создаёт контракт:

```
кошелёк ──деплой──> НОВЫЙ контракт продажи
кошелёк ──NFT─────> он же   (два шага, оба могут упасть по отдельности)
```

Отсюда следствие, которое ломает наивные ожидания: **между этими шагами NFT
может зависнуть**. Если деплой прошёл, а перевод нет — у вас пустой контракт.
Если перевод прошёл на неверный адрес — NFT потерян безвозвратно.

---

## 2. Что даёт tonutils (ПРОВЕРЕНО)

Интроспекция установленного пакета:

```python
NFTTransferBuilder(
    destination: AddressLike,          # кому передаём NFT
    nft_address: AddressLike,          # какой именно NFT
    response_address: AddressLike|None = None,   # куда вернуть излишек
    custom_payload: Cell|None = None,
    forward_payload: Cell|str|None = None,       # ← сюда идут условия продажи
    forward_amount: int = 1,           # нанотоны, пересылаемые получателю
    amount: int = 50000000,            # 0.05 TON на газ перевода
    query_id: int = 0,
    send_mode: SendMode|int = 3,
    bounce: bool|None = None,
)
```

`BaseNFTItem` — только чтение: `get_nft_data()`, `get_transactions()`,
`refresh()`, `run_get_method()`. Все асинхронные.

### Чего в tonutils НЕТ (ПРОВЕРЕНО)

Поиск по всем подмодулям `tonutils.contracts` по ключам
`sale` / `market` / `auction` / `getgems`:

- **модулей — НЕТ**
- **классов — НЕТ** (нашлись только `get_auction_info_get_method` и
  `get_telemint_auction_*` — read-only гет-методы, не создание продажи)

**Вывод: контракт продажи Getgems библиотека собирать не умеет.** Перевести
NFT она может, создать листинг — нет.

---

## 3. Три пути, и у каждого своя цена

### A. Контракт продажи Getgems — «настоящий» листинг

Лот появляется на Getgems, его видят покупатели, работает обычный флип.

**Проблема — ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ:** насколько мне известно, контракты
продажи Getgems при деплое требуют **подписи маркетплейса** (соглашение о
комиссии площадки). Если это так, произвольно развернуть свой контракт и
ожидать, что лот появится на Getgems, **нельзя** — нужен их бэкенд-эндпоинт,
выдающий подписанный payload.

**Это надо проверить до того, как писать код.** Практический способ: выставить
один лот вручную через интерфейс Getgems и посмотреть в explorer, какая
транзакция ушла — из неё видно и опкод, и структуру payload, и участвует ли
подпись площадки. Час работы, который экономит неделю догадок.

Если подпись нужна — путь A требует интеграции с приватным API Getgems, и это
уже совсем другой объём работ, чем «дописать функцию».

### B. Прямой перевод покупателю — работает на tonutils уже сейчас

`NFTTransferBuilder` умеет это без всяких контрактов продажи.

Но это **не флип**: покупателя надо где-то найти и как-то договориться об
оплате. Автоматизации рынка тут нет. Годится для вывода NFT на другой свой
кошелёк, не для торговли.

### C. Ручная продажа — то, что есть сейчас

Бот покупает, вы продаёте руками в Tonkeeper/Getgems и сообщаете боту цену
через `close_position(position_id, sell_price)`. Учёт PnL честный, бэктест
получает реальные данные.

**Именно это сейчас и реализовано** — `close_position()` существует, но её
никто не вызывает автоматически, это функция бухгалтерии.

---

## 4. Транзакция — меньшая половина работы

Даже когда путь A решён, «продавать» — это отдельный слой решений, которого
в боте **нет вообще**:

| Вопрос | Почему это не мелочь |
|---|---|
| **Когда выставлять?** | Сразу после покупки? Через час? Модель прибыли молча предполагает «сразу и по floor». |
| **По какой цене?** | `floor × (1 − undercut)` на момент покупки или на момент листинга? Floor уже уехал. |
| **Floor упал — что делать?** | Переставлять лот ниже (каждая переустановка = газ) или ждать? Без правила бот зависнет с неликвидом. |
| **Сколько ждать?** | Лот висит 5 дней. Фиксировать убыток? Держать? Без таймаута капитал замораживается и риск-лимиты перестают что-либо значить. |
| **Стоп-лосс** | Floor рухнул на 40%. Выходить или пересиживать? |
| **Отмена листинга** | Нужна отдельная транзакция; контракт продажи должен вернуть NFT. |

Бэктест сейчас моделирует выход как «через N часов по floor того момента».
Это **допущение, а не механика**: он не учитывает ни очередь у floor, ни то,
что ваш собственный лот двигает floor, ни отказ покупателей.

---

## 5. Честная оценка

**Покупка** — понятная задача: API проверен, нужен `sale.address`, исполнитель
и ворота testnet. Один заход.

**Продажа** — не задача «дописать функцию», а отдельный кусок работы:

1. выяснить протокол листинга Getgems (нужна ли подпись площадки) — **до кода**;
2. если подпись нужна — интеграция с их API, объём неизвестен, пока не выяснено;
3. двухшаговый деплой+перевод с обработкой зависания между шагами;
4. слой решений о продаже (таблица выше) — по объёму сопоставим с текущим
   слоем решений о покупке;
5. отмена и переустановка листинга;
6. тесты на всё это без сети.

---

## 6. Что рекомендую

**Не гнаться за полной автоматизацией обеих сторон сразу.** Осмысленная
последовательность:

1. **`--record` сейчас** — проверяет парсинг и копит данные, не требует ничего
   из вышеперечисленного.
2. **`--backtest` через 2–3 дня** — отвечает на вопрос, прибыльна ли стратегия
   вообще. Если прогноз расходится с фактом, всё остальное не имеет смысла.
3. **Покупка на testnet** — когда появится доступ к правкам торгового пути.
4. **Полуавтомат**: бот покупает, вы продаёте руками и вводите цену. Это даёт
   реальные данные о продажах — и они нужны, чтобы вообще понять, по какой
   цене и за какое время ваши лоты уходят.
5. **Автопродажа — последней**, уже зная из п.4 реальную механику рынка.

Пункт 4 не компромисс, а способ собрать данные, без которых слой решений о
продаже проектируется вслепую.

# РАЗВЯЗКА: как устроен листинг на Getgems (18.09.2026)

Главный открытый вопрос этого файла — «требует ли листинг подписи
маркетплейса». Пользователь купил Xmas Stocking #91332 и выставил его обратно;
ниже — что именно ушло в блокчейн.

ОТВЕТ, к которому привёл полный разбор тела: **скорее всего требует**. Сначала
здесь стоял обратный вывод — он был сделан по списку ИМЁН операций в
Tonviewer, где подпись не подписана отдельным полем. Разбор самих битов
показал в теле деплоя 512 бит, проходящих все структурные проверки ed25519,
и открытый ключ в хранилище контракта. Подробности — в разделе «ПОДПИСЬ
GETGEMS».

## Что видно в Tonviewer

```
a few seconds ago   Send NFT   UQAF...44KF  ->  Getgems Deplo...   Call: 0x00fe0ede
                    Send NFT   Getgems Deplo... ->  UQCc...FX5w
2 minutes ago       NFT Purchase  UQAF...44KF -> UQD6...SC3z       4.49 GRAM
```

После этого владельцем NFT значится `UQCc...FX5w` — новый контракт продажи.

## Механика (уточнено по Raw Transactions)

Сырые транзакции самого предмета показывают три шага. Ниже — дословно из
Tonviewer, `UQAF...44KF` — кошелёк владельца.

**Шаг 1. Листинг, транзакция `58763931...bc0829ff`:**

```
IntMsg  UQAF...44KF      -> предмет   +0.219 GRAM   nft_transfer
IntMsg  предмет -> Getgems Deployer   -0.2   GRAM   nft_ownership_assigned
IntMsg  предмет -> UQAF...44KF        -0.0156 GRAM  excess
```

Владелец шлёт **обычный `nft_transfer`** на сам предмет, где `new_owner` —
контракт-деплойер Getgems, а `forward_amount` = 0.2 GRAM. Предмет пересылает
деплойеру `nft_ownership_assigned` вместе с `forward_payload`, в котором и
лежат условия продажи.

**Шаг 2. Деплойер создаёт контракт продажи, транзакция `6f9a7576...f35b608e`:**

```
IntMsg  Getgems Deployer -> предмет   +0.178 GRAM   nft_transfer
IntMsg  предмет -> UQAF...44KF        -0.1787 GRAM  excess
```

Деплойер вторым `nft_transfer` переводит предмет на созданный контракт продажи.
Владельцем предмета становится этот контракт; продавец сохраняет право снять
лот и забрать NFT обратно.

**Для сравнения — покупка, транзакция `6775641b...9d5bdbf6`:**

```
IntMsg  контракт продажи -> предмет   +0.3187 GRAM  nft_transfer
IntMsg  предмет -> покупатель                       nft_ownership_assigned
IntMsg  предмет -> покупатель         -0.318 GRAM   excess
```

То есть покупатель платит контракту продажи, а тот отдаёт предмету команду
сменить владельца. Это подтверждает, почему `sale_address` обязателен: платить
надо контракту, предмет сам денег не принимает.

```
nft_transfer на АДРЕС ПРЕДМЕТА (op 0x5fcc3d14):
    new_owner            = 0:39d63083...c17e0e   (деплойер Getgems)
    response_destination = наш кошелёк
    custom_payload       = null
    forward_amount       = 200000000 нанотон (0.2 TON)
```

упирается всё не в сборку ячейки, а в подпись Getgems внутри неё.

## ПОЧЕМУ ЭТОМУ РАЗБОРУ МОЖНО ВЕРИТЬ

Разбор не проверяется тем, что «сошлось красиво». Здесь он проверен двумя
независимыми величинами, которые считаются ИЗ разбора и сверяются с тем, что
показал блокчейн:

1. **Хеш ячейки кода** из разобранного StateInit =
   `6b95a641...fb1feb86` — ровно тот, что Tonviewer показывает у
   задеплоенного контракта.
2. **Адрес контракта продажи** = `0:` + хеш всего StateInit =
   **`EQCcWUC7KPl_MXXsDHGt5GxJyP9Eo_54C88xBK89kSKKFSO1`** — ровно тот
   `EQCc...FSO1`, который появился в событиях транзакции.

Адрес контракта — это хеш StateInit целиком. Совпадение означает, что каждый
бит кода и данных разобран правильно: ошибись разбор хоть в одном бите, адрес
получился бы другим. Это и есть тот критерий сходимости, из-за которого op
0xfd135f7b был сначала опознан неверно (см. ниже).

## ПОДПИСЬ GETGEMS: 512 бит в теле деплоя

Те 512 бит проходят ВСЕ структурные проверки подписи ed25519:

| проверка | результат | вероятность случайного совпадения |
|---|---|---|
| вторая половина (S) < порядок группы L | да, старший байт `0x07` | ~3% |
| первая половина (R) — валидная точка кривой | да | ~50% |
| 256 бит в хранилище — валидная точка (открытый ключ) | да | ~50% |

Вместе — меньше 1% на случайность. То есть в хранилище контракта лежит
ОТКРЫТЫЙ КЛЮЧ, а в теле деплоя — подпись этим ключом.

**Что это значит.** Похоже, деплойер Getgems проверяет подпись своего
бэкенда, а её выдают в момент, когда пользователь жмёт «выставить» в
интерфейсе. Тогда листинг ЧЕРЕЗ ДЕПЛОЙЕР воспроизвести одним только кодом
нельзя — нужен ответ бэкенда Getgems.

Это ПРЯМО ПРОТИВОРЕЧИТ более раннему выводу в этом файле («подписи
маркетплейса в транзакции нет»). Тот вывод был сделан по именам операций в
Tonviewer, где подпись не подписана как поле. Правильным он не был.

ЧЕСТНО О СТАТУСЕ: это сильная улика, но не доказательство. Доказательством
была бы сошедшаяся проверка подписи, а для неё нужно знать, ЧТО именно
подписано. Проверены и не подошли: хеш StateInit, хеш data, хеш кода, хеш
payload, хеш корневой ячейки. Значит подписывается какая-то производная
(например, ячейка из query_id, адреса и параметров), и её состав ещё не
угадан.

## ГИПОТЕЗА, КОТОРУЮ НАДО ПРОВЕРИТЬ ДО ПОКУПОК

Подпись нужна ДЕПЛОЙЕРУ. Но деплойер, возможно, не нужен нам:

- код контракта продажи у нас есть дословно (он в сообщении);
- раскладка данных разобрана и проверена по адресу;
- адрес контракта считается детерминированно из StateInit.

Значит контракт продажи можно задеплоить САМИМ и перевести предмет прямо на
него — одним `nft_transfer` без участия деплойера и без подписи. Покупатель
платит контракту продажи, а не площадке, так что сторона покупки от этого не
меняется.

Чего это НЕ отменяет и почему нельзя считать вопрос закрытым:
- покажет ли Getgems такой лот на витрине — неизвестно; индексация идёт по
  хешу кода, и хеш у нас будет тот же, но проверить можно только опытом;
- поле на смещении 534 (`1000`, `0`) не опознано, а оно в блоке комиссий:
  ошибка здесь = контракт с чужой ставкой выручки;
- ошибка в раскладке = реально задеплоенный контракт с чужой ценой или чужим
  адресом получателя денег. Это НЕ откатывается.


## СМЕНА ЦЕНЫ (op 0xfd135f7b) — РАЗОБРАНО ПОЛНОСТЬЮ

Сообщение целиком, подтверждено на живой операции: владелец поменял цену
на 77, и в теле оказались ровно 77 TON.

```
b5ee9c72010101010014000023fd135f7b76a486ee80061f24511ed8ec2004

op        = 0xfd135f7b          (32 бита)
query_id  = 8549106351564267300 (64 бита)
new_price = 77000000000 = 77 TON  (coins)  <- ПОДТВЕРЖДЕНО
хвост     = 1 бит, равен 0
```

Уходит **на контракт продажи** (не на предмет), ссылок не имеет.
`0xfd135f7b` встречается и в коде самого контракта
(`8210fd135f7b52e0ba53c9c705b0`) — это его штатный обработчик.

**Это самая практичная находка для бота.** Перевыставить лот по другой цене
можно ОДНОЙ короткой транзакцией на контракт продажи: не забирая предмет, не
деплоя контракт заново и не собирая тот сложный payload на 2148 байт. Для
стоп-лосса и для подстройки под уехавший floor нужно ровно это.

Сообщение тривиально собирается: три поля, ни одной ссылки, ни одного
неопознанного бита.

ОГОВОРКА о происхождении этой записи: сначала op был определён как «снятие с
продажи» — по тому, что он встречается в коде контракта. Это оказалось
неверно: 45 бит, принятые за хвост, читаются как сумма, и она совпала с
выставленной ценой. Правильный признак — не наличие op в коде, а сходимость
значения с наблюдаемым действием.

## Как это доисследовать — ДИФФ ДВУХ ЛИСТИНГОВ

После полного разбора ячейки диффом закрываются ровно два вопроса, и покупать
ради них СРАЗУ НЕ НАДО (сначала — гипотеза о самостоятельном деплое выше):

1. **Что такое 34 бита на смещении 534.** Если при другой цене там снова
   `1000` и `0` — это ставка или константа, а не сумма. Если меняется вместе
   с ценой — это посчитанная комиссия.
2. **Подпись ли те 512 бит.** У подписи при другом предмете и другой цене
   меняются ВСЕ 512 бит без остатка; у хеша или счётчика так не выйдет.

Требования к опыту, иначе он не ответит ни на что:

- **тот же кошелёк** — иначе меняется адрес продавца, и это лишняя переменная;
- **та же коллекция** — иначе меняется адрес роялти;
- **цена заметная и некруглая** (например 3.33 TON) — круглое число труднее
  отличить от константы контракта;
- нужен полный текст «Copy Raw body», а не скриншот: строка в интерфейсе
  обрезана.

**Хватит ОДНОГО предмета.** Двух меняющихся полей (предмет и цена) достаточно:
оба значения известны заранее, поэтому в диффе их видно по позиции. Второй
предмет добавил бы контроль «та же цена, другой предмет», но стоит ещё около
5 TON — это половина банка ради уточнения, которое дифф и так покажет.


## Чего ещё не хватает, чтобы писать код

Раньше здесь стоял список «неизвестно содержимое payload». Он закрыт: payload
разобран и разбор проверен по адресу задеплоенного контракта. Осталось ровно
три пункта, и все три — не про сборку ячейки:

1. **Подпись Getgems.** Что именно подписано — неизвестно, а значит через
   деплойер листинг кодом не собрать. Обходной путь (деплой контракта продажи
   самим) описан выше и НЕ проверен.
2. **34 бита на смещении 534** в блоке комиссий (`uint16 = 1000`, `uint16 = 0`).
   Лежат рядом с адресами выручки, поэтому ошибка здесь стоит денег.
3. **Покажет ли Getgems самостоятельно задеплоенный лот** на витрине. Лот, о
   котором никто не знает, не продаётся, каким бы правильным ни был контракт.

Газ на листинг — **ИЗМЕРЕНО: 0.22 GRAM** (0.2 forward + 0.02 новому контракту).


## Подтверждённая экономика

Диалог выставления на продажу (цена 5 GRAM):

```
Marketplace fee    0.1 GRAM     = 2.0%
Creator Royalties  +0 GRAM
You Receive        4.9 GRAM
```

Комиссия берётся С ЦЕНЫ ПРОДАЖИ и вычитается из выручки продавца — ровно так,
как считает `compute_net_profit()`. Ставки 2% и 0 подтверждены в третий раз.

Диалог покупки того же лота:

```
NFT Price     4.49 GRAM   (includes service fee and creator royalties)
Service Fee   0.08 GRAM
Network Fee   0.3 GRAM    (the rest will be returned to your wallet)
```

Отсюда `PURCHASE_GAS_TON = 0.3`: столько прикладывает сам Getgems. Стоявшие
там раньше 0.1 были взяты с потолка, и недостача газа уронила бы транзакцию.

## Газ на листинг (измерено)

Диалог подтверждения в кошельке при выставлении лота:

```
0.22 GRAM будет мгновенно списано с вашего кошелька для оплаты комиссии.
~ 0.19 GRAM будет возвращено вам в течение нескольких минут.
```

То есть к сообщению листинга прикладывается **0.22**, безвозвратно уходит
**около 0.03**. Когда листинг будет писаться кодом, прикладывать надо 0.22 —
не меньше: излишек возвращается, недостача роняет транзакцию.

Сводка по газу за полный круг:

| Операция | Приложено | Израсходовано |
|---|---|---|
| Покупка | 0.30 | не измерено |
| Листинг | 0.22 | ~0.03 |

`GAS_FEE_TON = 0.15` в экономике — это оценка безвозвратной стоимости круга.
Измеренные 0.03 на листинге показывают, что она скорее консервативна, чем
занижена; менять её без измерения расхода на покупке не нужно.
