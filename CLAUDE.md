# CLAUDE.md — контекст проекта

Память проекта для будущих сессий. Сессия в чате не переживает перезапуск
контейнера; этот файл переживает.

## Что это

Снайпер NFT-подарков Telegram в сети TON. Ищет недооценённые лоты, считает
экономику перепродажи, проверяет решение через Claude и соблюдает риск-лимиты.

- `gift_sniper.py` — всё приложение одним файлом (так попросил пользователь)
- `test_gift_sniper.py` — тесты, сети не требуют. **Запускать перед каждым коммитом.**
- `SETUP.md` — что пользователь должен предоставить; главный документ для него
- `deploy/` — systemd-юнит и Dockerfile
- `TONUTILS_API.md` — проверенный API подписи транзакций (не по памяти)
- `SELLING.md` — разбор стороны продажи: почему это не зеркало покупки

## Принятые решения (не откатывать без причины)

**Экономика.** Комиссия и роялти берутся с цены ПРОДАЖИ, не покупки. Формула
из исходного ТЗ (`(Floor−Buy) − Buy×5% − gas`) систематически завышала прибыль
и была исправлена намеренно.

**Floor.** Считается как 5-й перцентиль по выборке в несколько страниц, а не
`min()` по первой. У API нет сортировки по цене; `min()` по 20 лотам из 50 000
— это не floor. Малая выборка → торговля пропускается.

`MIN_FLOOR_SAMPLE = 40`, и это не круглое число с потолка: P5 попадает на
индекс `(N-1)*0.05`, поэтому при N<40 перцентиль опирается на один-два самых
дешёвых лота и вырождается в `min()`. Первый живой прогон 17.09.2026 это
показал: выборка 27 дала floor 5.27 TON при 4.72 на витрине Getgems —
завышение на 12%, то есть в ОПАСНУЮ сторону (завышенный floor завышает
выручку от перепродажи). Порог поднимать можно, опускать — нет.

**Whitelist по адресу, не по имени.** Скам-коллекции копируют имя и картинки.
Адреса нормализуются (raw ↔ EQ.../UQ..., CRC16) перед сравнением.

**Оценка по ПОХОЖИМ лотам, а не только по floor коллекции.** Floor — это цена
самой дешёвой модели, поэтому лот с мусорной моделью ниже floor выглядит
выгодным, хотя конкурировать будет со своим сегментом, а не с коллекцией.
`eff_floor = min(floor коллекции, floor сегмента)` — минимум, потому что
выборка по сегменту меньше и доверия ей меньше; так оценка никогда не
ВЫРАСТЕТ относительно прежнего кода.

**Глубокая скидка без данных о похожих — отказ (`DEEP_DISCOUNT_PCT = 60`).**
Ошибка продавца и неликвид в цене выглядят ОДИНАКОВО; различает их только
сравнение с сегментом. Без него глубокая скидка — не сигнал, а неизвестность.
Умеренная скидка воротами не блокируется: проверка ставилась именно на
глубокую.

**`PREMIUM_MULT = 1.0` по умолчанию.** Красота номера и редкость НЕ влияют на
решение, пока пользователь не откалибрует премию по своей записи рынка. Любое
значение выше 1.0 увеличивает расчётную прибыль — это направление, в котором
теряют деньги.

**Проверки «переплата над floor» нет намеренно.** Она была недостижима:
прибыль возможна только ниже ~0.87×floor. Расчёт прибыли её поглощает.

**`decide_exit()` — вход и выход симметричны по устройству.** Решение о
выходе такое же детерминированное, и бэктест гоняет ЕГО ЖЕ через
`_simulate_exit()`. Стоп-лосс считается от ЦЕНЫ ПОКУПКИ (под угрозой деньги,
а не точность прогноза) и проверяется РАНЬШЕ срока удержания. Есть выдержка
`STOP_LOSS_MIN_HOURS`: на тонком рынке floor скачет от одного снятого лота,
и мгновенный стоп фиксировал бы убыток там, где floor вернулся бы сам.
Дыра в записи обесценивает только плановый выход — стоп сработал бы и на
первом снапшоте после перерыва.

**`evaluate_trade()` — единственный источник истины.** Бэктест обязан вызывать
ЕЁ ЖЕ. Бэктест по копии логики не проверяет ничего.

**Детерминированный фильтр идёт ДО Claude.** ИИ не может отменить отказ, поэтому
спрашивать его про отбракованный лот — платить за ответ ни о чём.

**`execute_blockchain_buy()` никогда не возвращает True, не совершив сделку.**
Иначе в БД появится позиция, которой нет, и учёт PnL станет фикцией.

**`--probe АДРЕС`** — диагностика на живых данных: для кошелька показывает
коллекции его NFT, для коллекции проверяет КАЖДОЕ поле парсера отдельно и
печатает сырой JSON там, где разбор не удался. Это инструмент закрытия пункта
«форма ответов не верифицирована»: чинить парсер по сырому ответу, не гадая.

**Ранжирование коллекций (`--rank`).** Метрика активности — оборот витрины:
сколько дешёвых лотов исчезло между снапшотами. Измеряется по
CANDIDATES_TO_ANALYZE лотам, а исчезновение = продажа ИЛИ снятие; различить
без истории сделок нельзя. Метрика СРАВНИТЕЛЬНАЯ: где активнее, а не сколько
продано. Различает три состояния: живая / замерла / офлайн — у них разные
причины и разные решения.

**Прерывистая запись — не то же самое, что короткая.** Если ПК выключают на
ночь, `_future_floor()` находит «снапшот через 24 часа» только следующим утром,
и бэктест засчитал бы 33-часовое удержание как суточное. Поэтому есть
`BACKTEST_MAX_SLACK_HOURS` (6ч): зазор больше — позиция НЕ закрыта, и отчёт
отдельно считает «дыра в записи» против «запись кончилась». Первое лечится
непрерывной записью, второе — ожиданием.

**Снапшот обязан помнить свою коллекцию.** Поле `collection` в записи; без
него бэктест подставляет floor чужой коллекции и считает мусор.

**Лимит TonAPI считается по секундам, а не по минутам.** Живой прогон поймал
429 на страницах 11–15 из 15 при интервале цикла 60с: интервал разносит ПАЧКИ
запросов, а страницы внутри пачки уходят подряд. Поэтому есть
`TONAPI_MIN_INTERVAL` (пауза между запросами) и ретраи на 429 — совет «подними
POLL_INTERVAL_SEC» от этого не спасает. Ретраить обязательно: молча потерянная
страница прореживает выборку, а floor по тонкой выборке ЗАВЫШАЕТСЯ.

**У анонимного доступа к TonAPI есть СУТОЧНАЯ квота.** Дословный ответ сервера
(снят в браузере 17.09.2026):
`{"error":"rate limit: anonymous tier daily traffic is spent, resets at UTC midnight"}`

Это принципиально не то же самое, что «слишком часто». Ждать надо ЧАСЫ, поэтому:
- суточная квота распознаётся по телу ответа и НЕ ретраится вовсе;
- выставляется метка `_tonapi_quota_until` до ближайшей полуночи UTC, и до неё
  запросы к TonAPI даже не отправляются — жечь исчерпанный лимит незачем;
- после полуночи бот возобновляет работу сам, без перезапуска.

Обычный 429 («слишком часто») ретраится как раньше — путать эти два случая
нельзя, есть тесты на оба. Лимит выделен в исключение `RateLimited`, и при нём
обход страниц коллекции ПРЕКРАЩАЕТСЯ: дограбливать оставшиеся 14 страниц
бессмысленно, при пяти коллекциях это 70 мусорных запросов за цикл.

Сообщение обязано называть и срок сброса, и лечение (бесплатный ключ на
tonconsole.com) — иначе пользователь крутит POLL_INTERVAL_SEC, который тут
совершенно ни при чём.

**Суточный бюджет запросов (`TONAPI_DAILY_BUDGET`, 10000).** Ключ TonAPI
снимает ограничение по частоте, но НЕ снимает суточное: 5 коллекций x 15
страниц каждые 120с — это 54 000 запросов в сутки, и живой прогон 18.09.2026
сжёг квоту даже с ключом, уйдя в слепоту до полуночи.

`budget_paced_interval()` растягивает интервал цикла так, чтобы остатка
бюджета хватило ровно до полуночи UTC. Механизм умеет только ЗАМЕДЛЯТЬ —
разогнать бота ниже `POLL_INTERVAL_SEC` он не может. Интервал считается, а не
задаётся: число коллекций и глубина выборки меняются, и подобранная руками
цифра станет неверной на седьмой коллекции.

Почему замедление лучше слепоты: редкий шаг всего лишь огрубляет наблюдение,
а дыра в записи ОБЕСЦЕНИВАЕТ сделки в бэктесте (см. `BACKTEST_MAX_SLACK_HOURS`).

Расход СОХРАНЯЕТСЯ В БД (`api_budget`, ключ — дата UTC) и поднимается при
старте. Квота живёт на стороне TonAPI, а счётчик — в памяти процесса: без
сохранения бот, перезапущенный в обед, считает бюджет нетронутым и добивает
остаток. Это тот же принцип, по которому в БД лежат риск-лимиты: лимит,
обнуляющийся при рестарте, — не лимит. Сброс на диск идёт каждые
`_BUDGET_FLUSH_EVERY` (25) запросов и в конце цикла; сбой записи не роняет
наблюдение, но предупреждает. Запись за ПРОШЛЫЕ сутки не берётся — квота
сбрасывается в полночь, и вчерашний расход замедлил бы бота зря.

Уменьшать `FLOOR_SAMPLE_PAGES` ради экономии квоты НЕЛЬЗЯ: выставленных лотов
в коллекции единицы процентов, и выборка падает пропорционально страницам.
Живой прогон дал 33/63/42/48/82 при 15 страницах — на восьми первая коллекция
ушла бы ниже `MIN_FLOOR_SAMPLE`, и торговля по ней пропускалась бы ВООБЩЕ.
Правильный рычаг — интервал (его крутит бюджет сам), а не глубина выборки.

**Запасной источник Getgems GraphQL МЁРТВ**: `403 Forbidden` на
`api.getgems.io/graphql` (18.09.2026). Считать его фолбэком больше нельзя —
при исчерпании квоты TonAPI данных нет вообще.

**Несколько коллекций.** `TARGET_COLLECTIONS` — список; у каждого типа подарка
свой контракт и свой floor, смешивать их нельзя. Обработка независимая: сбой
одной коллекции не роняет остальные. Нагрузка на API растёт ЛИНЕЙНО по числу
коллекций — preflight предупреждает при >100 запросов/мин.

**Коллекция выбирается под банк (`--afford`).** Потолок сделки — это
`MAX_POSITION_PCT`% банка, и при банке 10 TON он равен 1 TON. Коллекция с
floor 4.72 при этом недостижима: прибыльная покупка там стоит до 3.97 TON,
и риск-лимит отрежет КАЖДУЮ сделку. В логе это выглядит буднично
(«заблокировано лимитом»), поэтому проверку вынесли в отдельный режим — до
записи рынка, а не после недели наблюдений. Диапазон ограничен с двух сторон:
сверху потолком сделки, снизу газом (при floor 0.3 нужна скидка 63%, при
1.0 — 28%). «Чем дешевле, тем лучше» — неверно.

**Повышенный лимит по ROI (`MAX_POSITION_PCT_HIGH_ROI`) по умолчанию ВЫКЛЮЧЕН**
(равен обычному). Смысл механизма: плоский процент от банка слеп к качеству
сделки. Цена: высокий расчётный ROI — ровно то место, где модель ошибается
чаще всего (глубокая скидка чаще означает причину, а не ошибку продавца), так
что повышение ставки идёт туда, где оценке меньше всего оснований доверять.
Включать только после бэктеста по своей записи.

ВАЖНО при расчётах доступности: требование «ROI >= 100%» режет цену покупки
ВДВОЕ сильнее, чем «хоть какая-то прибыль» (`buy <= K/(1+ROI/100)`). Считать
повышенный потолок против границы безубыточности нельзя — получится вывод
«дорогая коллекция доступна при скидке 18%» там, где нужно 59%. Есть
регрессионный тест.

**Сводка в Telegram ограничена по частоте (`HEARTBEAT_MIN`, 60 мин).**
Молчащий бот неотличим от упавшего, но уведомление каждую минуту перестают
читать через час — и пропускают то единственное, ради чего оно было нужно.
Стартовое сообщение называет фактические настройки: на Windows переменные
живут в одном окне cmd, и тихий старт с чужими значениями портит запись.

**Банк и ключ.** `BANKROLL_TON` — граница, за которой денег нет; `RESERVE_TON`
не тратится никогда (иначе не на что продать). Ключ читается только из файла
с правами 0600 — не из переменной окружения, её видно в `ps`.

## Что НЕ сделано и почему

**ПОКУПКА НАПИСАНА** (18.09.2026). `_send_purchase()` шлёт платёж на контракт
продажи через `tonutils`; API взят из **`TONUTILS_API.md`** — не переделывайте
это исследование заново. `REAL_EXECUTOR_AVAILABLE` теперь определяется
УСПЕХОМ ИМПОРТА, а не константой: без библиотеки живой режим закрыт заранее,
а не падает в момент покупки.

Правки торгового пути раньше отклонялись классификатором среды («real-world
transactions») — в этой сессии прошли. Попытка отредактировать собственные
разрешения по-прежнему граница, которую не обходят: правило в settings.json
пишет пользователь, не Claude.

`tonutils` — НЕОБЯЗАТЕЛЬНАЯ зависимость. Имена `_TonapiClient`, `_NetworkGlobalID`
и прочие при провале импорта выставляются в None, а `_trading_network()` бросает
понятное «tonutils не установлен, pip install...» вместо NameError: «имя не
определено» отправляет искать ошибку в коде вместо того, чтобы поставить пакет.
Тесты обязаны проходить И БЕЗ библиотеки — проверки выбора сети в секции [31]
пропускаются, но проверка понятной ошибки остаётся. Поймано прогоном
пользователя на Windows, где пакета не было.

НЕ ПРОВЕРЕНО ЖИВЬЁМ: ни одна транзакция ещё не отправлялась. Первый прогон
обязан быть на **testnet** (`TRADING_NETWORK=testnet`, это значение по
умолчанию; нераспознанная строка тоже даёт testnet — есть тест).

`PURCHASE_GAS_TON` (**0.3**) — газ СВЕРХ цены, контракту на исполнение и
пересылку NFT; излишек возвращается. Это ДРУГАЯ величина, чем `GAS_FEE_TON`
в экономике (безвозвратная стоимость круга). Путать нельзя.

0.3 — столько прикладывает САМ интерфейс Getgems («Network Fee 0.3 GRAM — the
rest will be returned», снято с диалога покупки 18.09.2026). Раньше стояло 0.1,
взятое с потолка: недостача газа не экономит, а роняет транзакцию — контракт не
доисполнится и NFT не придёт. Излишек возвращается, поэтому ошибка вверх
бесплатна, а вниз стоит сделки. Есть тест на нижнюю границу.

**Экономика подтверждена живой сделкой.** Диалог продажи при цене 5 GRAM:
комиссия площадки 0.1 (2.0%), роялти +0, «You Receive 4.9». То есть комиссия
берётся с ЦЕНЫ ПРОДАЖИ и вычитается из выручки продавца — ровно как в
`compute_net_profit()`.

**Продажи нет как кода**, но ГЛАВНЫЙ ВОПРОС ЗАКРЫТ (18.09.2026). Разобрано по
сырым транзакциям живого листинга:

1. владелец шлёт `nft_transfer` НА ПРЕДМЕТ, где `new_owner` = деплойер Getgems,
   `forward_amount` = 0.2, а условия продажи лежат в `forward_payload`;
2. предмет пересылает деплойеру `nft_ownership_assigned` с этим payload;
3. деплойер вторым `nft_transfer` переводит предмет на созданный контракт продажи.

**ЯЧЕЙКА `0x00FE0EDE` РАЗОБРАНА ПОЛНОСТЬЮ** (18.09.2026) — из того же тела
«Copy Raw body», без новых покупок. Раскладка в `SELLING.md`.

Разбор ПРОВЕРЕН, а не предположен: из него считается адрес контракта продажи
(`0:` + хеш StateInit) и получается `EQCcWUC7...kSKKFSO1` — ровно тот, что
появился в блокчейне, и хеш ячейки кода тоже совпал с Tonviewer. Адрес — хеш
StateInit целиком, поэтому ошибка хоть в одном бите дала бы другой адрес. Это
тот же критерий сходимости, из-за которого op `0xfd135f7b` сначала опознали
неверно.

**ПОДПИСЬ МАРКЕТПЛЕЙСА, СКОРЕЕ ВСЕГО, ЕСТЬ — прежний вывод «её нет» ОТМЕНЁН.**
Он был сделан по списку ИМЁН операций в Tonviewer, где подпись не выделена
отдельным полем. В теле деплоя (op `0xfb5dbf47`) лежат 512 бит, проходящие все
структурные проверки ed25519 (S < L со старшим байтом 0x07, R — валидная точка
кривой), а в хранилище контракта — 256 бит, тоже валидная точка, то есть
открытый ключ. Случайность такого совпадения — меньше 1%.

Значит листинг ЧЕРЕЗ ДЕПЛОЙЕР Getgems кодом не собрать: подпись выдаёт их
бэкенд в момент нажатия «выставить». Доказательством была бы сошедшаяся
проверка подписи, но для неё надо знать, ЧТО подписано; хеши StateInit, data,
кода, payload и корня проверены и не подошли.

ОБХОДНОЙ ПУТЬ, который надо проверить ДО новых покупок: деплоить контракт
продажи САМИМ. Код контракта приходит в сообщении дословно, раскладка данных
разобрана и проверена по адресу, адрес считается детерминированно — то есть
предмет можно перевести одним `nft_transfer` прямо на свой контракт, без
деплойера и без подписи. Непроверенное в этом пути: покажет ли Getgems такой
лот на витрине, и что означают 34 бита на смещении 534 в блоке комиссий
(`uint16 = 1000`, `uint16 = 0`) — они лежат рядом с адресами выручки.

`NFTTransferBuilder` из `tonutils` покрывает внешнее сообщение целиком, кроме
`forward_payload`. Подробности с дословными строками — в `SELLING.md`.

Там же подтвердилось, почему `sale_address` обязателен: при покупке платят
КОНТРАКТУ ПРОДАЖИ, а он уже командует предмету сменить владельца. Сам предмет
денег не принимает.

Сообщение листинга РАЗОБРАНО по Tonviewer (детали в `SELLING.md`):
- op `0x5fcc3d14` (`nft_transfer`) на адрес ПРЕДМЕТА;
- `new_owner` = деплойер Getgems
  `0:39d63083e48f46452ff8a04cd0d3733a90c8be299aa5951b62741759b2c17e0e`;
- `forward_amount` = 200000000 нанотон (0.2 TON), приложено к сообщению 0.22;
- `forward_payload` = ячейка с op `0x00FE0EDE` (16649950), BOC 2148 байт;
- деплоится контракт с интерфейсом **`nft_sale_getgems_v4`** — раскладка
  данных у v3r3 и v4 разная, писать надо под v4.

**СМЕНА ЦЕНЫ РАЗОБРАНА ПОЛНОСТЬЮ** и собирается тривиально:
`op 0xfd135f7b` (32) + `query_id` (64) + `new_price` (coins) + 1 нулевой бит,
на АДРЕС КОНТРАКТА ПРОДАЖИ, без ссылок. Подтверждено живой операцией: владелец
поставил 77, в теле ровно 77 TON. Перевыставить лот дешевле можно ОДНОЙ
транзакцией — не забирая предмет и не деплоя контракт заново. Для стоп-лосса
и подстройки под уехавший floor нужно именно это.

Урок методики: сначала этот op был определён как «снятие с продажи» на том
основании, что он встречается в коде контракта. Неверно. Признак — не наличие
op в коде, а СХОДИМОСТЬ декодированного значения с наблюдаемым действием.

**Дифф двух листингов НЕ СРОЧЕН и покупок пока не требует.** Раскладка уже
известна; диффом закрываются только два вопроса — что такое 34 бита на
смещении 534 и подпись ли те 512 бит. Когда дело до него дойдёт, хватит ОДНОГО
предмета: тот же кошелёк, та же коллекция, заметная некруглая цена. Второй
предмет дал бы контроль «та же цена, другой предмет» за лишние ~5 TON —
половину банка ради уточнения, которое дифф покажет и так.

`close_position()` — по-прежнему бухгалтерия, её никто не вызывает
автоматически.

Пробел, который надо закрыть вместе с подписью:
- `REAL_EXECUTOR_AVAILABLE` должен зависеть от **успеха импорта** tonutils,
  а не быть константой: иначе бот упадёт в момент покупки вместо того,
  чтобы не стартовать заранее.

**Платёж уходит на контракт продажи, а не на NFT** — адрес теперь сохраняется
(`sale_address` из `sale.address` TonAPI), вместе с площадкой (`sale_market`).
`execute_blockchain_buy()` отклоняет лот без `sale_address` — и отклоняет ДО
ветки DRY_RUN: симуляция, рапортующая успех там, где живая покупка невозможна,
врала бы о готовности бота. Запасной источник (Getgems GraphQL) этот адрес не
отдаёт вовсе, поэтому его лоты годятся для floor, но не для покупки.

**Форма ответа TonAPI ЧАСТИЧНО ПРОВЕРЕНА** на живых данных 17.09.2026
(коллекция Timeless Books). Секция [19] тестов построена на дословном ответе.

Подтверждено работающим:
- `collection.address` есть → whitelist работает (EQ-форма матчит raw);
- трейты в `metadata.attributes` как `{trait_type, value}` → разбираются;
- номер минта берётся ТОЛЬКО из `metadata.name` ("... #16450").

**Верхнеуровневый `index` — НЕ номер минта.** В реальных данных это огромное
отрицательное число (-181007727810587533). Не «чинить» парсер, начав его
использовать: есть регрессионный тест.

**Процентов редкости в API НЕТ**, хотя интерфейс Getgems их показывает —
Getgems считает их сам. Оценка по выборке остаётся единственным путём.

**Форма поля `sale` ПОДТВЕРЖДЕНА** на выборке в 50 предметов (выставлены
были 3 из них): `sale.address` — контракт продажи, `sale.price.value` —
нанотоны строкой, `sale.market.name` — площадка. Секция [20] тестов построена
на этих дословных блоках.

**Площадок несколько, и бот видит их ВСЕ сразу.** TonAPI читает блокчейн, а не
базу одного маркетплейса, поэтому лоты с разных площадок приходят вперемешку
в одном ответе — отдельный обход площадок не нужен. В одной коллекции
встретились «Getgems Sales» и «Marketapp Marketplace».

Общий floor их УСРЕДНЯЕТ, и в этом усреднении прячется разница цен между
площадками, то есть арбитраж. Поэтому снапшот несёт `market_floors` (floor
по каждой площадке отдельно), а `--markets` считает разброс по записи.
Оценкой это НЕ управляет: разница может означать разные комиссии, разный
состав лотов или тонкий рынок на одной из площадок, и отличить можно только
по записи за несколько дней. Комиссии в отчёте считаются одинаковыми для всех
площадок — реальные ставки сняты только с Getgems.

Купить на площадке можно только когда бот умеет говорить с её контрактом
продажи. Протоколы могут отличаться; подписи транзакции для этого мало.

**Вопрос валюты закрыт: GRAM — это нативная монета TON.** Рядом с
`token_name: "Gram"` стоят `currency_type: "native"` и `decimals: 9`. Значит,
допущение о нанотонах верно, и экономика в TON ничего не ломает. Интерфейс
Getgems просто подписывает нативную монету как GRAM.

**`--discover` НЕ проверен на живых данных.** Эндпоинт списка коллекций
(`/v2/nfts/collections`) в этом проекте ни разу не вызывался; сеть к tonapi.io
из среды разработки закрыта. Написан так, чтобы при неожиданном ответе
вернуть None и напечатать сырой JSON, а НЕ пустой список: пустой список
читается как «подходящих коллекций нет» и увёл бы поиск не в ту сторону.
`[]` (искали, не нашли) и `None` (не разобрали) — разные вещи, есть тест.

**Комиссия площадки для Telegram-подарков — 2%** (справка Getgems, 18.09.2026):
5% с продажи вообще, 1% для Anonymous Telegram Numbers и Usernames, **2% для
Telegram-подарков**. Бот работает с подарками, поэтому `MARKETPLACE_FEE_PCT=0.02`.
Сходится с карточкой лота: 0.09 GRAM на цене 4.75 = 1.9%.

Этот параметр уже дважды ставили неверно, и оба раза незаметно: завышенная
комиссия тихо отклоняет сделки («рынок плохой»), заниженная тихо завышает
прибыль. Поэтому есть тест, секция [30], фиксирующий 0.02.

Оговорки: для коллекции, которая НЕ является Telegram-подарком, нужно 0.05.
У других площадок (Marketapp) ставка своя и не проверена — отчёт `--markets`
считает комиссии одинаковыми для всех.

**Роялти создателя = 0** (`ROYALTY_PCT=0`). Проверено на ТРЁХ независимых
лотах из разных коллекций подарков (18.09.2026): Easter Egg, Valentine Box,
Jester Hat — везде Creator Fee 0 GRAM. Там же ещё раз подтвердились 2%
площадки: 0.11/5.5, 1.48/74, 0.09/4.89.

ИСКЛЮЧЕНИЕ: лот Bunny Muffin на площадке «Other» показал Creator Fee
**0.45 GRAM** при комиссии площадки 0 — то есть на не-Getgems площадках
разбивка другая, и ноль там занижает издержки.

**Покупать разрешено только на проверенных площадках (`ALLOWED_MARKETS`,
по умолчанию «Getgems Sales»).** Не перестраховка: у того же Bunny Muffin
адрес контракта продажи СОВПАДАЛ с адресом самого предмета — протокол там
другой. Платить туда по нашей схеме значит отправлять деньги вслепую, и
потерять можно всю сумму, а не её часть. Проверка стоит ДО ветки DRY_RUN.
Пустой список отключает проверку — это осознанный выбор оператора.

ОСТАЁТСЯ НЕПРОВЕРЕННЫМ:
1. **Сторона bid.** У коллекции показан Instant Sell (3.94 при floor 4.72) —
   это мгновенный выход, которого в модели нет вовсе: она считает только
   продажу по floor c undercut.

## Правила работы с этим репозиторием

- Секреты только через окружение/файл с правами 0600. Ключ не логировать,
  не писать в БД, не слать в уведомлениях.
- Перед коммитом: `python test_gift_sniper.py` — должно быть «ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ».
- **Тесты ГЕРМЕТИЧНЫ и обязаны такими остаться.** В начале файла блок `_PINNED`
  фиксирует ВСЕ настраиваемые величины на значения по умолчанию, потому что
  настройки читаются из окружения при импорте. Запуск в окне cmd, где стоял
  `set BANKROLL_TON=10`, ронял «нормальная сделка проходит»: банк 10 минус
  позиция 10 минус резерв 1 = −1. Тест, сравнивающий с глобальной переменной,
  меряет чужую конфигурацию, а не код. Проектные решения («комиссия 2%»,
  «повышенный лимит выключен») проверяются по ЗНАЧЕНИЮ ПО УМОЛЧАНИЮ в
  исходнике, а не по текущей переменной.
- **Windows: POSIX-прав нет.** `os.chmod()` там управляет только флагом
  «только чтение», `st_mode` всегда 0o666/0o444. Проверка `mode & 0o077`
  отвергала бы ЛЮБОЙ файл ключа, и живая торговля на Windows была бы
  невозможна с советом про chmod, которого там не существует. Поэтому на
  `os.name == "nt"` проверка заменена на громкое предупреждение: ворота не
  ослаблены, а честно признаны непроверяемыми. Тесты прав там пропускаются.
- Не ослаблять ворота живого режима «чтобы заработало».
- Изменения, увеличивающие расчётную прибыль, требуют обоснования данными,
  а не рассуждением.
